# 파일 정본 사용자 데이터

리스바드의 사용자 데이터 정본은 이름별 폴더에 펼친 JSON·JSONL·Markdown과 이미지·음성 등의 일반 파일입니다. SQLite와 `database.bin`은 정본이 아닙니다. 기존 클라이언트와 RisuAI 내보내기에 필요한 `database.bin`은 파일 정본에서 다시 만들 수 있습니다.

서버 실행 전에 절대 데이터 루트를 지정할 수 있습니다.

```bash
RISUBARD_DATA_ROOT=/private/path/risubard-data node server/node/server.cjs
```

데이터 루트에는 분리된 설정·credential, 이름별 엔터티 폴더, 메시지 JSONL, 로그, 작업별 state/event, 에셋과 BardWiki가 있습니다. 일반 화면의 시작·저장은 문서 API를 사용하며, `database.bin`을 읽거나 전체 DB를 다시 인코딩하지 않습니다. 화면에 남아 있는 DB 형태의 객체는 호환용 메모리 캐시이지 디스크 정본이 아닙니다.

- 캐릭터: `characters/<이름>/character.json`, `description.md`, `first_mes.md`, `lorebook.json`, `assets/`
- 대화: `characters/<이름>/chats/<대화 이름>/metadata.json`, `messages.jsonl`, 필요시 `draft.json`
- 프롬프트 프리셋: `prompts/<이름>/settings.json`, 프롬프트 본문별 `.md`
- 모듈: `modules/<이름>/module.json`, `description.md`, `lorebook.json`, `assets/`
- 페르소나: `personas/<이름>/persona.json`, 프롬프트 `.md`, `assets/`
- 아직 소유자가 정해지지 않은 업로드·전역 배경·구형 미분류 에셋: `shared/assets/` (캐릭터·모듈 간 이미지 공유를 뜻하지 않음)

실제로 존재하는 필드만 별도 파일로 추출합니다. 각 `manifest.json`은 본문 파일과 내부 필드를 연결합니다. Risumari처럼 사람이 찾아보기 쉬운 구성이지만 Risumari 폴더와 직접 교환 가능한 동일 규격은 아닙니다.

같은 종류·같은 부모 아래 이름이 겹치면 `이름`, `이름 (2)`, `이름 (3)`으로 구분합니다. Windows 금지 문자·대소문자·이름 길이로 발생하는 충돌도 피합니다. 표시 이름의 중복을 금지하거나 원래 ID를 바꾸지 않습니다. 폴더 경로는 순서 기록에서 ID에 연결되므로 이름 변경 후에도 캐릭터·대화·모듈 등의 참조가 유지되며, 기존 형제 폴더의 번호를 다시 매기지 않습니다.

## 디스크에서 직접 편집하기

앱에서 해당 내용을 편집 중이지 않을 때 `.md`, 로어북 JSON, 에셋 파일을 수정하고 브라우저를 새로고침하세요. **이미지는 같은 경로·파일명으로 교체**하면 다음 요청에 반영됩니다. 창을 켜 둔 채 즉시 바뀌는 실시간 감시 기능은 아닙니다. 이미지 파일의 확장자와 형식은 맞춰 유지하는 것을 권장합니다. 내부 ID, `manifest.json`, `settings/entity-order.json`, `settings/asset-files.json`을 수동 변경하거나 폴더를 탐색기에서 임의로 옮기지 마세요.

다른 V2 세이브의 캐릭터·모듈 등을 현재 세이브에 합칠 때는 폴더를 직접 복사하지 말고 **시스템 → 백업 → V2 항목 가져오기**를 사용하세요. 서버 PC에 있는 원본 V2 세이브 경로를 입력하면 항목과 연결 대상을 먼저 보여 줍니다. 선택한 항목이 참조하는 모듈·페르소나 등은 자동으로 함께 가져오며, 같은 ID는 새 ID로 바꾸고 실제 ID 참조 필드만 같이 갱신합니다. 같은 이름의 폴더에는 번호를 붙이고, 같은 논리 이미지 키의 서로 다른 파일도 별도 키와 별도 파일로 보존합니다. 원본은 읽기 전용으로 열고 미리보기 이후 원본이 바뀌면 실행을 거부합니다. 대상은 롤백 가능한 하나의 journal로 반영하므로 검증·에셋 복사·게시 실패 시 현재 세이브를 시작 전 상태로 되돌립니다.

캐릭터·모듈·페르소나가 같은 옛 이미지 키를 참조하더라도 소유자별로 참조와 실제 파일을 분리합니다. 한 소유자의 파일을 바꾸면 다른 소유자에게 전파하지 않으며, 이미지 내용이 같다는 이유로 합치거나 편집 가능한 파일을 하드링크하지 않습니다. 복제된 항목도 독립 참조를 받습니다. 캐릭터·모듈·페르소나 자체의 ID는 유지합니다. 선택 중인 페르소나를 보여 주는 전역 사용자 아이콘은 해당 페르소나 이미지의 표시 참조이므로 같은 파일을 사용합니다. 기존 V2의 다중 소유자 참조는 전체 호환 저장·가져오기 또는 오프라인 업그레이드에서 분리합니다. 네이티브 저장은 해당 문서에 새로 추가한 참조만 소유자별로 처리하고 서버가 승인한 새 참조를 화면에 반영합니다.

V2의 새 이미지 저장과 검증된 백업 가져오기는 일반 에셋 파일에만 쓰고 KV 오브젝트를 이중 생성하지 않습니다. 아직 소유자가 없는 업로드는 `shared/assets/`에서 시작합니다. 소유자가 정해지면 소유 폴더의 파일과 참조가 게시되고 내용이 일치하는 것을 확인한 뒤, 더 이상 참조하지 않는 해당 업로드 파일만 제거합니다. 외부 수정으로 내용이 달라진 파일이나 복구용 `.bak`는 이 과정에서 삭제하지 않습니다. 매핑된 에셋이나 본문을 잃었을 때는 옛 캐시로 조용히 되돌리지 않습니다. KV에는 여전히 DB·설정 등 비에셋 호환 데이터와 구형 복구 오브젝트가 있으므로 폴더 전체를 삭제하면 안 됩니다. 기존 이미지 KV 참조를 해제할 때도 이전 manifest를 복구용으로 남기고 오브젝트 자체는 자동 삭제하지 않습니다. 따라서 참조 해제와 실제 디스크 여유 공간 회수는 별개입니다.

새로 저장한 데이터는 `settings/entity-order.json`에 항목 소속과 순서를 보존합니다. `index/sidebar.json`이 사라지거나 손상돼도 이 기록과 정본 파일에서 목록을 복구해 프롬프트·채팅 선택 순서를 유지합니다. 순서 기록이 없는 구형 데이터는 목록을 잃었을 때 원래 순서를 보장하지 못합니다. 메시지 본문 파일이 사라졌다면 빈 대화로 저장하지 않고 오류를 표시하므로 백업에서 해당 데이터를 복구해야 합니다.

V1·V2에서 두 목록 기록이 모두 사라졌거나 빈 인덱스 때문에 기존 항목이 보이지 않으면 [남은 V1·V2 파일에서 목록 복구하기](recover-save-index.md)를 따르세요. 오프라인 도구가 실제 항목 파일을 읽어 별도 세이브 복사본에 목록을 재구성하며, V1 복사본은 검증 후 V2로 변환합니다. 원본은 변경하지 않으며 중복 ID·본문 누락 등은 보고서에 남기고 완성본 게시를 중단합니다.

저장은 같은 파일시스템의 temp 작성, fsync, checksum/schema 검증, 원자 rename, 부모 디렉터리 fsync, `.bak` revision과 복구 가능한 다중 파일 journal을 사용합니다. 삭제는 `trash/`로 이동합니다. 일반 저장은 변경된 문서만 처리하고 그 안에서도 내용이 동일한 파일은 다시 쓰지 않습니다. 대화 본문 변경은 해당 대화의 `messages.jsonl`을 저장하며, 아직 모든 메시지 편집이 append 방식인 것은 아닙니다.

## 네이티브 문서 런타임

이관 안내의 `로컬 백업 생성`은 선택 사항입니다. 같은 기기의 기존 보관 폴더 절대 경로를 입력하면 그 안에 고유한 `RisuBard-backup-.../data/` 폴더를 만들고 원본 전체를 복사·검증합니다. `.bin` 다운로드가 아닌 원본 폴더 백업이며, 완료 화면에 데이터 경로·복구 안내 파일 경로·완료 시각을 표시합니다. 복구 방법은 함께 저장되는 `backup-info.json`에 있습니다. 백업 후 자동으로 이관하지 않으므로 `이관 시작` 또는 `프로그램 종료`를 선택할 수 있습니다. 백업 중에는 다른 작업을 막으며 공간 부족·검증 실패 시 완료로 표시하지 않습니다. 별도 백업은 추가 용량을 사용하고, 이관 때 보존하는 원본 폴더와는 별개입니다.

구형 저장소로 서버를 시작하면 저장소 초기화보다 먼저 같은 기기의 `http://localhost:<포트>/`에서 V2 이관 동의를 받습니다. 원본 보존 경로는 데이터 루트와 같은 상위 폴더의 `backups/<저장폴더명>.v1-<고유값>/`입니다. 거부하면 앱 서버는 시작하지 않고 종료합니다. 필요한 여유 공간은 새 V2 문서·소유자별 에셋·보조 파일의 실제 생성 계획에 파일시스템 할당 단위와 여유분(최소 64MiB 또는 할당 추정량의 5%)을 더해 계산합니다. 원본 크기의 3배를 일괄 요구하지 않으며, 같은 이미지를 여러 소유자에게 독립 저장하는 경우에는 각각 계산합니다. 실행 중에도 파일별로 남은 공간을 재검사합니다. 추정치는 예약된 공간이 아니므로 실행 중 공간 부족도 실패할 수 있습니다.

원본을 읽기 전용으로 읽어 빈 임시 폴더에 V2 파일을 직접 생성하고 에셋 검증·전체 데이터 왕복 검사·재열기를 수행합니다. KV 에셋이나 옛 휴지통을 통째로 복제하지 않으며, 초안·위키·인레이·플러그인 KV와 보조 파일을 새 저장소에 보존합니다. SQLite 원본은 읽기 중 sidecar 변경을 막기 위해 DB와 WAL/SHM만 별도로 복사하며 이 용량도 추정에 포함합니다. 원본 파일의 해시와 폴더 구성이 바뀌면 적용하지 않습니다. 검증 후 기존 저장소 전체를 백업 위치로 이동하고 V2 임시 폴더를 원래 경로로 옮깁니다. 기존 휴지통과 복구 기록도 원본 백업에 남으며 그 용량은 자동 회수되지 않습니다. 두 폴더 교체 사이에 중단되면 다음 시작에서 원본을 복구합니다. 처음부터 빈 저장소 또는 V2인 경우와 앱에서 직접 외부 백업을 가져오는 경우에는 이 동의 화면을 생략합니다.

- 시작할 때 설정과 전체 항목 ID·이름·썸네일 등의 목록 요약을 읽습니다. 캐릭터·모듈 본문은 선택·편집·실행 시 준비하고, 캐릭터를 열면 그 캐릭터의 대화 목록 메타데이터를 읽습니다. 대화 본문은 필요할 때 읽습니다.
- 페르소나·프롬프트 프리셋·전역 로어북은 기존 동기식 편집 화면과의 호환을 위해 시작 시 개별 문서로 읽습니다. 모든 컬렉션이 완전히 지연 로딩되는 구조는 아닙니다.
- 목록 요약과 로딩 중 자리표시자는 저장 기준선이 아닙니다. 문서마다 읽은 내용의 revision과 마지막으로 승인된 값을 별도로 관리합니다. 목록 일부를 읽지 않았다는 이유로 삭제하지 않습니다.
- 저장 도중 새로 입력한 내용은 저장 응답이 덮어쓰지 않습니다. 외부 파일과 같은 문서를 동시에 수정하면 충돌로 거부하고 로컬 편집을 유지합니다. 최신 파일 확인 없이 구형 전체 DB 저장으로 우회하지 않습니다.
- 문서의 변경 여부는 JSON 필드 순서가 아닌 실제 값으로 비교합니다. 읽기와 저장 완료 응답이 같은 문서의 반복 저장을 일으키지 않으며, 저장 대기 대상은 꺼낸 뒤 비워 새 편집만 다시 예약합니다.
- 409 충돌에는 충돌한 문서와 최신 revision이 포함됩니다. 해당 문서를 다시 읽어 기존 기준선·로컬 편집·최신 파일을 비교하고, 서로 다른 필드의 편집만 합쳐 한 번 재시도합니다. 같은 필드·메시지 배열의 동시 편집이나 삭제·목록 변경은 자동 병합하지 않습니다. 해결하지 못한 충돌은 로컬 내용을 유지한 채 같은 요청의 자동 재시도와 반복 알림을 중단하며, 충돌하지 않은 다른 문서는 계속 저장합니다.
- 이름 변경은 내부 ID를 유지합니다. 폴더 이동 중 하위 메시지·초안·에셋이 외부에서 바뀌면 게시 전에 중단합니다. 중단된 journal 재생 때 파생 checksum 파일이 정본을 덮어쓰지 않도록 처리합니다.
- `settings/native-runtime.json`은 문서 런타임 표시입니다. 전환 시 활성 `database/database.bin` 캐시 참조는 제거하지만 구형 복구 오브젝트를 임의로 삭제하지 않습니다. 정상 네이티브 읽기·저장은 이 큰 캐시를 재생성하지 않습니다.

전체 상태가 필요한 예외는 구형 백업 가져오기·내보내기와 명시적인 구형 API 호환 요청입니다. 신·구 클라이언트가 섞여 접속하면 이미 승인한 구형 저장을 먼저 완료한 뒤 문서 요청을 처리합니다. 호환 API의 외부 변경 검사는 유지하지만 네이티브 문서 요청마다 전체 트리를 검사하지 않습니다.

기존 동기식 전체 데이터 API를 사용하는 활성 구형 플러그인은 실행 전에 필요한 문서들을 미리 읽는 호환 경로가 필요합니다. 이때 메모리에 더 많은 문서가 올라올 수 있지만 `.bin`을 조립해 일반 저장하지는 않습니다. 불완전한 메모리 캐시만 보고 에셋을 자동 삭제하는 작업은 네이티브 클라이언트에서 수행하지 않습니다.

기존 `.bin`과 save-folder 가져오기는 임시 저장소에서 원격 블록·콜드 스토리지를 복원하고, 이름별 폴더와 실제 에셋 파일로 변환한 뒤 전체 데이터의 왕복 일치를 확인합니다. 가져오기 성공 시 이미 새 파일 구조가 게시되어 있으며 첫 화면 로딩까지 변환을 미루지 않습니다. 새 레이아웃은 `settings/layout.json`의 `schemaVersion: 2`로 구분합니다. 아직 새 레이아웃이 없는 저장소는 최초 네이티브 문서 요청 시 일회성 호환 가져오기를 거치거나 아래 리허설 도구로 미리 변환합니다. 이것은 리스바드 저장 레이아웃 V2이며 원본 RisuAI의 외부 백업 규격을 바꾸는 것은 아닙니다.

사용자 화면에서는 별도의 데이터 이전 페이지와 원본 Risu용 내보내기·save-folder 수동 가져오기를 제공하지 않습니다. 전체 백업 다운로드·복원은 **시스템 → 백업**에만 있으며 기존 로컬 백업과 RisuAI 백업도 이 복원 경로에서 계속 변환합니다. V2 세이브끼리 일부 항목만 합치는 경우에만 위의 V2 항목 가져오기를 사용합니다.

현재 **모듈 에셋을 제외한 설정 백업**은 모듈의 이미지 참조만 남기므로, 새 저장소의 엄격한 가져오기 검증에서 거부됩니다. 설정을 다른 인스턴스로 옮길 때는 모듈 에셋도 포함하세요. 의도적으로 제외한 파일과 손상으로 누락된 파일을 구분하는 호환 처리는 아직 릴리즈 전 해결 과제입니다.

누락된 대화 본문, 중복 ID, 손상된 블록, 정본 트리와 호환 데이터의 불일치는 기존 저장소 교체 전에 거부합니다. 정상적인 빈 목록을 포함한 가져오기는 교체이므로, 사용자에게 보이는 기존 목록은 교체됩니다. 이전 정본 폴더와 KV manifest는 `trash/import-<id>/`에 남고, 해당 manifest가 참조하는 에셋은 자동 정리에서도 보존됩니다. 복구 기록을 삭제하면 이 보존도 해제되므로 검증 전에는 지우지 마세요.

정본·인레이·KV manifest는 하나의 복구 journal로 게시합니다. 게시 중 디스크 오류가 나면 후속 접근을 막으며, 재시작 시 준비된 journal을 재생합니다. 검증 실패와 게시 중단은 서로 다릅니다. 후자는 재시작 후 새 데이터로 완료될 수 있으므로 오류가 났다고 즉시 다른 백업을 덮어쓰지 마세요.

옛 `risuai.db`는 `migration-backups/`에 복사한 뒤 한 번만 가져오며 정상 런타임은 SQLite에 의존하지 않습니다. 전체 백업은 파일 정본 트리, 에셋, BardWiki·소설 프로젝트와 호환 내보내기 데이터를 포함합니다.

## Docker의 기존 세이브 이관

Docker 이미지는 이관 안내 서버를 외부에서 연결할 수 있도록 `RISUBARD_MIGRATION_HOST=0.0.0.0`을 사용합니다. `docker logs risuai-nodeonly`에 표시된 `migration-token`이 포함된 링크를 열고, 다른 기기에서는 `localhost`를 Docker 호스트 주소로 바꾸세요. 접근 키는 서버 시작 때마다 바뀌며, 키 없는 외부 접속은 세이브 상태를 읽거나 이관·백업을 실행할 수 없습니다. 일반 포터블은 기본적으로 같은 기기의 localhost에서만 이관할 수 있습니다.

Docker의 `RISUBARD_MIGRATION_IN_PLACE=1`은 볼륨 연결 지점인 `save` 자체를 이동하지 않습니다. 사전 검사의 임시 파일, 변환본, 잠금과 복구 기록은 볼륨 안의 예약 폴더 `.risubard-v2-migration/`에서 관리합니다. 원본 사용자 파일은 검사 중 변경하지 않습니다. 이관이 끝나면 원본 전체는 `save/.risubard-v2-migration/backups/save.v1-<고유값>/`에 남습니다. 기존 휴지통도 여기에 보존되며, 이 폴더를 지우면 원본 복구본도 없어집니다.

파일 교체 중 종료되면 다음 시작에서 원본 항목을 복구한 뒤 다시 동의를 받습니다. 다른 이관 작업이 살아 있으면 복구·이관을 동시에 실행하지 않습니다. Linux에서는 프로세스 시작 식별자까지 확인하므로 컨테이너 재시작으로 같은 PID가 재사용되어도 이전 작업의 잠금으로 오인하지 않습니다.

선택 사항인 `로컬 백업 생성`에는 별도로 마운트한 영구 백업 폴더의 컨테이너 내부 경로를 입력하세요. 이 전체 폴더 백업은 `.risubard-v2-migration/` 안의 원본 보존본도 포함합니다. 기존 `risuai-nodeonly_risuai-save` 볼륨을 삭제하거나 빈 볼륨으로 교체하지 마세요.

## 원본을 변경하지 않는 이관 리허설

서버를 종료한 뒤 아래 도구에 기존 경로와 **존재하지 않는 별도 출력 경로**를 지정합니다. 현재 파일 KV 또는 구형 hex 파일 폴더를 대상으로 하며, SQLite 전용 폴더·정본만 남은 폴더는 별도 검토가 필요합니다.

```powershell
node scripts/rehearse-save-migration.cjs 'E:\old-save' 'E:\save-rehearsal'
```

원본은 읽기만 하고 활성 파일의 해시를 비교합니다. 출력의 `snapshot/`은 격리 복사본, `converted/`는 새 포맷 테스트 데이터, `report.json`은 결과입니다. 초안과 보조 파일을 옮기고 기존 ID 트리는 `trash/layout-<id>/`에 보존합니다. 호환 DB 기준으로 변환하므로 기존 정본과 호환 DB가 이미 갈라져 있다면 `snapshot/`과 추가 대조해야 합니다. `converted/`를 실제 저장 경로로 자동 전환하지 않습니다. 테스트 복사본에도 비밀키가 포함될 수 있으므로 공유하거나 공개 저장소에 넣지 마세요.

이미 만들어 둔 **격리 리허설 스냅샷만** 다시 사용할 때는 `--reuse-snapshot <기존 snapshot 경로> <새 출력 경로>`를 지정할 수 있습니다. 이 모드는 변경 불가능한 KV 오브젝트를 하드링크할 수 있으므로 실제 활성 세이브를 입력하지 마세요. 편집 가능한 엔터티·에셋 파일은 독립 복사본입니다.

사용자가 이미 삭제했다고 확인한 모듈의 메타데이터가 구형 저장소에 남아 있다면 `--exclude-module-id <정확한 ID>`를 반복 지정해 **변환 복사본에서만** 제외할 수 있습니다. 해당 모듈의 활성화·소속 참조도 정리하고 제외 내역을 보고서에 남깁니다. 원본에 없는 ID는 오류로 거부합니다. 이미지 누락만 보고 모듈을 자동 삭제하지 않으며 원래 메타데이터는 스냅샷과 변환 휴지통에 보존됩니다.

Termux에서는 `$HOME/.local/share/risubard` 같은 앱 내부 저장소를 사용하세요. 공유 `/sdcard`와 `/storage/emulated`는 신뢰할 수 있는 fsync·원자 rename을 보장하지 않아 정본 루트로 거부됩니다. 공유 저장소에는 완성된 백업 파일만 복사하세요.
